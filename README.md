# Task_2 — API-тесты Stellar Burgers

22 независимые проверки пяти эндпоинтов. Для каждого эндпоинта создан отдельный тестовый класс.

## Запуск

```bash
python -m venv .venv
```

Windows: `.venv\Scripts\activate`. Linux/macOS: `source .venv/bin/activate`.

```bash
python -m pip install -r requirements.txt
python -m pytest --alluredir=allure-results --clean-alluredir
allure serve allure-results
```

Готовый автономный отчёт открывается файлом `allure-report/index.html`.
Для генерации такого же отчёта через Allure 3:

```bash
allure generate allure-results --config allurerc.json --output allure-report --clean
```

Адрес по умолчанию: `https://qa-stellarburgers.education-services.ru`.
Для другого стенда задайте переменную окружения `STELLAR_BASE_URL` без `/api`.

## Покрытые сценарии

| Класс | Проверки |
| --- | --- |
| TestCreateUser | Уникальный пользователь, повторная регистрация, отсутствие email/password/name |
| TestLogin | Успешный вход; неверный email, пароль и оба поля |
| TestUpdateUser | Изменение email, имени и пароля с авторизацией и без неё |
| TestCreateOrder | Заказ с авторизацией и без неё, ингредиенты, пустой список, отсутствие поля, неверный хеш |
| TestGetOrders | Собственные заказы с исключением чужих, запрос без авторизации |

Пользователи получают уникальные адреса на домене example.com. Успешно зарегистрированные пользователи удаляются после теста, в том числе после падения проверки. У заказа нет документированного эндпоинта удаления; очищается владелец заказа. Заказ без авторизации нельзя связать с пользователем для очистки.

Фикстуры подготавливают данные и обрабатывают HTTP-ошибки; тестовые assert находятся в тестах. В отчёте есть запросы и ответы, пароли и токены скрыты.

## Результат проверки 23.11.2026

20 passed, 2 failed. Ошибок подготовки и удаления тестовых пользователей нет. Тесты не пропускаются и не помечены xfail.

Две проверки выявляют расхождения стенда с документацией, приложенной к уроку (`api-Stelar_Burger_10.25.pdf`):

1. **Заказ без авторизации.** На странице 5 сказано, что заказы могут делать только авторизованные пользователи. Тест ожидает отказ 401, как для остальных защищённых ручек. Фактически POST `/api/orders` возвращает 200 и номер заказа. Код отказа именно для создания заказа отдельно не указан; это место требует уточнения контракта.
2. **Неизвестный хеш ингредиента.** На странице 1 указан ответ 500. Фактически передача `ffffffffffffffffffffffff` (24 шестнадцатеричных символа, отсутствует в каталоге) возвращает 400 с телом `{"success":false,"message":"One or more ids provided are incorrect"}`. В тесте сохранено ожидание 500 из задания; формат тела ответа 500 документация не определяет. Отдельная проверка некорректного формата `invalid-hash` также дала 400.

Ожидаемое поведение не заменено фактическим ради зелёного отчёта. Детали запросов и ответов сохранены в Allure.
